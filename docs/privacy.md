# Privacy

Tablemate's data inventory: what is collected, how it is protected, how long it is kept and how it is
erased. It documents the behaviour of the code in this repository (AAP 0.5.2, 0.5.3, 0.3.2, 0.5.5);
where the code differs from the plan's rule, the difference is marked **Deviation** with the rule it
departs from, so a reviewer can act on it.

Two words are used precisely throughout. A **pseudonymous** record still carries a linking key — an
account id, a meetup id, a keyed pair hash — and is retained on that basis. An **unlinked** record
carries no such key. Nothing here is called anonymous unless no key reconnects it to a person.

The circuit the itinerary proof is built from, its seven public signals and its issuer registry are in
[zk-proofs.md](./zk-proofs.md); the retention period and the call rules that await counsel's review are
in [legal-review.md](./legal-review.md).

## Principles

- **The itinerary email never reaches the server.** The device parses the `.eml`, builds the circuit
  inputs and proves locally, then transmits `{ proof, publicSignals }` and nothing else. The seven
  public signals are `cityId`, `arrivalDate`, `departureDate`, `issuerId`, `nullifier`, `registryRoot`
  and `nullifierSalt` (`PUBLIC_SIGNAL_NAMES`, `packages/shared/src/schemas/proofs.ts`). The guest name,
  the booking reference, the address, the price and the email text appear in none of them, and
  `ProofSubmission` is strict at both levels, so an unknown key is refused. The server holds no proving
  key, no circuit WASM and no witness generator, and no route accepts a private input.
- **The `.eml` stays on the device.** The bytes live in memory only. On native, a copy the app made
  into its own cache, temporary, inbox or share-intent directory is deleted in a `finally` on success,
  failure and cancellation alike, and a URI the app does not own — a `content://` path, or the
  traveller's original — is never deleted or written
  (`apps/mobile/src/zk/eml-intake.native.ts`). The web prover holds the bytes in a Worker that is
  terminated after every attempt or cancel. Client state keeps `{ status, issuerId?, errorCode? }`, and
  logs carry error codes, never email bytes, field values or private inputs.
- **Location is used only for the check-in test.** The permission is requested by the check-in flow
  alone. The submitted coordinates are bound parameters of one `ST_Distance` query and nothing more:
  they are never a column value, an outbox payload, an analytics prop, a notification or a log field.
  A check-in row holds its result, a distance bucket (`lt_50` under 50 m, `m50_150` up to the 150 m
  geofence) and a failure code (`apps/api/src/modules/meetups/check-in.ts`).
- **The profile is pseudonymous.** A generated handle and avatar seed stand for the traveller; a real
  name, a photo and a phone number are never required. Profile fields are released by viewer-and-target
  tier and enforced at field level in the API, so no field above the caller's tier leaves the server
  (`apps/api/src/modules/users/disclosure/`).
- **Analytics user ids exist only as a salted hash.** `AnalyticsEvent.actorHash` is HMAC-SHA256 of the
  account id under `ANALYTICS_SALT`, and the table has no foreign key to `User`
  (`apps/api/src/modules/analytics/emit.ts`). That hash is pseudonymous, not anonymous, until erasure
  removes it.
- **No raw card data at the API, and no call audio anywhere.** Card entry happens only inside Stripe's
  own UI components, and no request schema accepts a card field. Twilio recording is off and is not a
  parameter any caller can turn on (`record: false`,
  `packages/server-core/src/telephony/twilio-client.ts`); no Voice Intelligence service is attached and
  no audio is stored.

## Account deletion (`DELETE /v1/me`)

`requestDeletion` applies the disposition in one order (`apps/api/src/modules/me/deletion.ts`):

- **One transaction, with the account's row locked first.** It takes `SELECT … FOR UPDATE` on `user`,
  sets `deletionRequestedAt` (first write wins, so the instant of the first request survives a second
  one), revokes every session and refresh token, deletes the account's lodging claims with their
  booking details, plans the `delete_customer` `PaymentOperation`, and writes the `account_erasure`
  outbox row that announces the erasure. A session row _is_ the refresh token, so revoking the rows
  ends both.
- **The write fence closes the account to writes the moment that commits.** Every mutating handler,
  the state-writing reads (proposal detail, suggestions and the operator's audited booking-details
  read) and every WebSocket write first takes
  `SELECT … FOR SHARE` on the acting account's row and refuses with `401 token_invalid` once deletion
  is requested. The check reads PostgreSQL, never the cache, and a mutation already in flight holds its
  share lock, so the deletion waits for it to commit: nothing the account wrote can commit after the
  deletion commits, and the erasure runs only afterwards.
- **Redis invalidation follows the commit.** The session cache entry `auth:session:<sid>` lives 30
  seconds; the deletion publishes an invalidation on `user:<userId>` that makes every API instance drop
  its cached entries and close the account's sockets. An instance that misses the message can serve
  reads for at most 30 seconds and can never carry a write.
- **Meetups.** A `proposed` meetup is cancelled with reason `account_deleted`. A `locked` one without
  an open dispute follows the cancellation rule for the current time — free at or before
  `startsAt − 2 h`, otherwise a late-cancel forfeit, so deletion cannot escape a forfeit. A `locked`
  one with an open dispute is left for the operator with its holds and dispute intact, because a
  manual decision has to read the conversation. A single meetup whose cancellation raises is logged and
  counted; the remaining meetups still run and the erasure is queued either way.
- **Lodging claims.** Every claim is deleted with its booking details, including one in `calling`,
  which the user-facing route refuses with `409 call_in_progress`: its task is cancelled, a live call
  has its attempt marked `superseded` so the relay speaks its closing line and hangs up, and the result
  is never applied.
- **Payments.** The `delete_customer` operation carries its own copy of the Stripe customer id, so the
  erasure job can clear `User.stripeCustomerId` without losing it. The executor runs it only once every
  deposit of the account is final (`released`, `captured`, `refunded` or `expired`) and no dispute on
  its meetups is open, and nulls the copied id in the transaction that records success.
- **Erasure.** `account-erasure` runs after the transaction commits, again when the last open dispute
  resolves, and in a daily sweep. The sweep warns at 25 days, which leaves an operator five days to
  resolve the dispute holding an erasure open, and enforces the 30-day limit even if the re-queue is
  lost.

## Third parties and exceptions

| Processor                  | Data shared                                                                                                                                     | Note                                                                                                                                                                                                                                                                                                                                                                                                       |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Stripe                     | An opaque customer id, PaymentIntent ids and amounts, the setup and hold references                                                             | No email, name or phone number is sent: profiles are pseudonymous, so a new customer is an empty object and a saved card is a payment-method reference. Card data never reaches the API — card entry and 3-D Secure run in Stripe's own UI components. Stripe runs in test mode wherever `APP_ENV` is not `production`, and the API refuses to start outside production with a key that is not a test key. |
| Twilio Programmable Voice  | The business's phone number, the fixed per-language dialogue templates, and — for a lodging call only — the guest's booking name and stay dates | Recording is off, no Voice Intelligence service is attached, and no audio is stored. The call reaches only an allowlisted number outside production.                                                                                                                                                                                                                                                       |
| Language-model provider    | Menu page text for extraction, and the callee's utterances for classification                                                                   | Never user profile data. The booking name is replaced by `<guest>` in the classification request before it is sent, window and latest utterance alike (`apps/api/src/modules/voice-agent/understanding.ts`), so the model sees no guest name even when the callee repeats the one the relay spoke.                                                                                                         |
| OpenStreetMap Overpass API | No user data: city bounding boxes and place queries                                                                                             | Attribution is shown wherever place data appears.                                                                                                                                                                                                                                                                                                                                                          |
| Menu websites              | No user data: page fetches for a place's published menu                                                                                         | Restricted to operator-allowed domains, after a `robots.txt` check, at one request per second per domain.                                                                                                                                                                                                                                                                                                  |
| Expo push and SMTP         | Push tokens for registered devices; the email address for magic links and web notifications                                                     | Email is the fallback where the recipient has no registered device, which is the only channel a browser has. A recipient who is erased or deleting is sent nothing, and the delivery row is acknowledged rather than retried.                                                                                                                                                                              |

**The lodging-verification exception.** Verifying a stay is the one place Tablemate discloses something
about a traveller to a third party: the automated call tells the lodging that a guest with the booking
name is staying from one date to another, which is an explicit exception to the zero-knowledge
principle the rest of the product rests on. The app states it before consent can be given, the API
requires `callConsent: true` before the claim is created, and the booking details are encrypted at rest
and erased once the claim resolves. A lodging call's transcript is never stored, so the name survives
only in the ciphertext columns and in the live call.
